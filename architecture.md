# Architecture

## Crates
- `schema` — versioned `SceneV1`/`ScenePatchV1` types and validation (`crates/schema`).
- `daemon` — TCP, loopback-only service holding named scenes in memory with revisioned, atomic patches (`crates/daemon`).
- `renderer` — wgpu GPU compositor: shapes/images/SVG/text, MSAA+supersampling AA, PNG/GIF export (`crates/renderer`).
- `cli` — `renderer-cli` binary; one-shot render, `daemon serve`, `scene` subcommands, `show` (`crates/cli`).
- `mcp` — `renderer-mcp` binary; stdio JSON-RPC server exposing the tools above to agent hosts (`crates/mcp`).
- `terminal` — shared inline-preview logic (cmux/Kitty/iTerm2/system-viewer protocol detection), used by both `renderer show` and the MCP `show_image` tool (`crates/terminal`).

## Renderer crate layout

`crates/renderer` (package `renderer-core`) is split into focused modules; `lib.rs` only declares them and re-exports the public API (`GpuRenderer`, `RenderedImage`, `RenderError`).

- `gpu/` -- `mod.rs`: `GpuRenderer` and adapter/device setup (`new`), `MSAA_SAMPLE_COUNT`, `SUPERSAMPLE_FACTOR`; `render.rs`: the public `render_png`/`render_gif`/`render_rgba` entry points; `frame.rs`: `FrameTargets`, `record_frame`/`finish_frame`, effect pipeline; `analytic.rs`: the experimental analytic-AA (`*_analytic_aa`) path.
- `composition/` -- turns a scene into GPU draw commands (`composition_plan`; `analytic.rs` for the analytic-AA variant).
- `tessellation.rs`, `analytic_geometry.rs`, `fill.rs`, `vertex.rs` -- CPU-side geometry, fills/gradients, vertex formats.
- `pipelines.rs`, `shaders.rs` -- wgpu render pipelines and the WGSL sources.
- `assets.rs`, `svg.rs`, `limits.rs` -- image/glyph decoding + the per-export `AssetCache`, SVG rasterization, resource limits.
- `animation.rs`, `gif.rs`, `util.rs`, `error.rs` -- keyframe interpolation, shared-palette GIF encoding, small helpers, error types.
- Tests sit beside the code they cover (`mod tests`), with GPU/golden tests in `gpu/tests/` and shared helpers in `test_support.rs`.

## Other crates' module layout

Each crate's `lib.rs` (or `main.rs` for `mcp`) only declares modules and re-exports the public API; tests sit beside the code they cover.

- `schema` -- `scene`, `node`, `fill`, `timeline`, `patch`, `limits`, `error`, `validate` (one versioned type family per module).
- `daemon` -- `protocol` (wire types), `error`, `endpoint` (loopback check), `store` (revisioned scenes), `daemon` (`RendererDaemon`), `server` (TCP loop, `serve`, `spawn_embedded`), `client` (`DaemonClient`), `metrics`.
- `terminal` -- `show` (`run`, `ShowRequest`/`ShowOutcome`), `protocol` (detection), `target` (tty/ancestor discovery, system viewer), `kitty`, `iterm2`, `frames`, `cmux_preview` (unix; `cmux_preview_stub.rs` elsewhere), `error`.
- `mcp` -- `main.rs` (stdio loop, `respond`), `tools` (tool definitions), `schema` (JSON Schemas), `handlers` (tool calls, daemon endpoint), `output`, `inspect`.

## MCP call flow
agent → `renderer-mcp` (stdio JSON-RPC) → `daemon` (127.0.0.1, in-memory named scenes, revisioned patches) → `renderer` (wgpu GPU pass) → `.renderer/output` (PNG/GIF + `metrics.jsonl`) → `renderer-terminal` → terminal/cmux preview.

The MCP `initialize` response carries `instructions` telling agents to auto-open every rendered image/GIF via `show_image`.

`render_scene` and `show_image` work without a daemon. The named-scene tools use the daemon at `RENDERER_DAEMON_ENDPOINT` if one answers there; otherwise `renderer-mcp` starts one itself on a background thread (`renderer_daemon::spawn_embedded`, resolved in `resolve_daemon_endpoint`), on the configured address or a free loopback port. That embedded daemon lives and dies with the MCP process and writes no metrics files.

## Known constraint: daemon client I/O timeout
`DaemonClient` hardcodes a 5s read/write timeout (`CLIENT_IO_TIMEOUT`, `crates/daemon/src/client.rs`). `export_named_gif` (and any daemon round trip) on a scene with enough frames/canvas area can exceed this before the daemon finishes rendering + GIF-encoding + responding, failing with `daemon connection failed: Resource temporarily unavailable (os error 35)` rather than a clean timeout error.

Measured on this machine: a 1000x420 canvas, 120-frame (24fps, 5s) timeline took ~5.5s end-to-end via the CLI's one-shot renderer — already over the daemon-path budget. Dropping to 60 frames (12fps) brought a full `export_named_gif` round trip in comfortably under 5s.

No env var or CLI flag currently exposes `CLIENT_IO_TIMEOUT`; raising it (or making it configurable) would let agents animate busier scenes through the MCP tools without needing to hand-tune frame counts.

## Performance work done (2026-09-18)

- **Daemon is now concurrent, not serial.** `serve_with_metrics_dir`'s accept loop (`crates/daemon/src/lib.rs`) used to call `handle_connection` inline, so one slow request (e.g. a multi-second `export_named_gif`) blocked every other connection, including trivial `get_scene`/`health` calls. `RendererDaemon` now holds `renderer: Arc<GpuRenderer>` (immutable, no lock needed -- `GpuRenderer`'s render methods touch no shared mutable state) and `scenes: Arc<Mutex<SceneStore>>` (locked only long enough to read/update the map, released before a render starts), and is `Clone`, so the accept loop spawns a thread per connection. Verified live: a `health` call issued mid-flight during a ~2.6s GIF export returned in ~0ms instead of waiting.
- **Per-export GPU texture reuse.** The composite/MSAA render targets, effect pipeline/texture/bind group, and the CPU readback buffer used to be allocated fresh on every single animation frame inside what is now `render_frame_with_targets` (`crates/renderer/src/gpu/frame.rs`). They're now built once per export by `create_frame_targets` (sized only by canvas dimensions and effect presence, both scene-level and non-animatable) and reused across every frame. Golden-image tests confirm byte-identical output (same SHA-256 before/after on a real render).
- **Measured, and this was the actual finding:** texture-reuse alone barely moved the needle on wall-clock GIF export time for a representative scene (still ~43ms/frame marginal cost). Isolating it (1 vs 10 vs 60 frames, no keyframes, same node complexity) showed the ~43ms/frame is dominated by something else in the GIF path -- almost certainly per-frame NeuQuant color quantization (the `image` crate's `GifEncoder` re-quantizes every frame independently; see the "Speed 10" comment at `crates/renderer/src/gpu/render.rs` in `render_gif_with_asset_root`). A single-frame PNG render of the same scene took ~80ms including GPU init, confirming the GPU composite/readback itself is cheap.
- **Shared GIF palette, implemented (2026-09-18).** `render_gif_with_asset_root` now renders every frame into one flat buffer first, then `encode_gif_with_shared_palette` (`crates/renderer/src/gif.rs`) writes the GIF directly via the lower-level `gif`/`color_quant` crates instead of `image`'s high-level `GifEncoder`: an exact, lossless palette when the whole animation fits in 256 colors (mirrors `gif::Frame::from_rgba_speed`'s own fast path, just applied across every frame instead of one), falling back to one shared `NeuQuant` network otherwise. Transparency handling mirrors `from_rgba_speed` too: any non-zero alpha becomes opaque, and the first fully-transparent pixel found pins the one color the whole animation's single transparent index maps to.
  - **First attempt was a regression, not a win** -- worth remembering: naively training `NeuQuant` on every frame's pixels concatenated made a 120-frame export *slower* (6.36s vs. 5.5s), because `color_quant::NeuQuant::learn`'s cost scales linearly with however many bytes it's handed divided by `samplefac` -- it has no notion of "this is already enough." Concatenating `frame_count` frames just means training on `frame_count`x more data; total training work came out roughly the same as the `frame_count` independent per-frame trainings it was meant to replace.
  - **The actual fix:** train the shared network on a bounded, evenly-strided sample (`PALETTE_TRAINING_PIXEL_BUDGET = 200_000` pixels, `subsample_for_palette_training`) instead of every pixel of every frame, so training cost stays roughly constant regardless of frame count. Every real output pixel still gets mapped to the trained palette afterwards via `NeuQuant::index_of` -- a cheap nearest-neighbor lookup (`search_netindex`'s early-exit search over a green-channel-sorted index), not a training update -- so quality doesn't suffer from the palette itself only having *trained* on a sample.
  - **Result:** marginal per-frame cost on the same representative scene dropped from ~43ms to ~28ms (isolated the same way, 1/10/60/120 frames). The demo animation used to build this repo's own MCP-loop GIF (1000x420, 120 frames, 24fps) previously had to be retimed down to 60 frames/12fps to survive the daemon's 5s `CLIENT_IO_TIMEOUT`; after this fix it completes at full 120 frames/24fps through the real `export_named_gif` MCP tool, no retiming needed.
  - Golden-image and GIF-decode tests (`renders_a_gif_with_static_assets_across_frames_on_an_available_gpu`, `shares_a_decoded_asset_cache_across_simulated_gif_frames`, `renders_golden_scenes_within_tolerance_on_an_available_gpu`) all still pass; the analytic-AA GIF path (`render_gif_with_asset_root_analytic_aa`) is untouched and still uses the old `image`-crate per-frame path, per its own doc comment guarantee of staying separate.

## Chasing 40fps further (2026-09-18, same day)

After the shared-palette fix, a 1000x420/120-frame export ran at ~35.7fps-equivalent (~28ms/frame) -- close to a 40fps target but not quite there. Two more changes were investigated:

- **Pipelined frame submission, implemented, measured no benefit.** `record_frame`/`finish_frame` (split from the old `render_frame_with_targets`) let a GIF export submit frame N+1's GPU work (into whichever of `FrameTargets::output_buffers` -- now two, ping-ponged -- frame N isn't reading back from) before waiting on frame N's readback, instead of fully blocking each frame. Correct and tested (byte-identical output), but measured **zero** wall-clock improvement (3.72s before and after on the same scene). Diagnostic conclusion: the bottleneck wasn't CPU idle time waiting on the GPU (which this would fix) -- it's CPU-bound work that happens *after* the readback and can't be overlapped with anything. Kept anyway since it's harmless and may matter more if per-frame CPU cost drops further.
- **Isolated the real remaining cost** with a throwaway in-process benchmark (not committed): pure GPU composite+readback+downsample (`render_rgba`, no GIF encoding at all) was ~24.4ms/frame -- almost the entire budget. That pointed at the CPU-side Lanczos3 downsample (`SUPERSAMPLE_FACTOR` composites at 2x linear resolution, i.e. 4x the pixels, then downsamples every single frame) as the actual dominant cost, not GPU raster time or GIF quantization.
- **Downsample filter switched from Lanczos3 to Triangle** (`finish_frame`, `crates/renderer/src/gpu/frame.rs`). `SUPERSAMPLE_FACTOR` always downsamples by exactly 2x; for an exact integer ratio, a triangle/linear filter approximates averaging each 2x2 source block -- the textbook-correct supersampling-AA downsample, not an approximation of a general-purpose resize. Lanczos3's much wider kernel (support radius 3 vs. Triangle's 1) was the real cost. Measured: ~30% faster (3.72s -> 2.61-2.63s on the same 120-frame scene, ~21ms/frame, ~47fps-equivalent) -- comfortably past 40fps.
  - **First attempt at reverting a side experiment corrupted unrelated code**, worth remembering: a global `sed 's/Triangle/Lanczos3/'` to undo a throwaway Lanczos3->Triangle test also silently "reverted" three *pre-existing, unrelated* `FilterType::Triangle` call sites (raster `image`-node scaling to declared node size, nothing to do with supersampling) back to `Lanczos3`, since by that point they all matched the same string. Caught via `git diff` before it went anywhere. Lesson: revert experiments by line number or `git checkout <path>`, never a blind global pattern replace, once more than one call site could share the changed text.
  - **Visually verified before committing to it**: rendered the same scene through both filters at native res, upscaled 10x with nearest-neighbor (no new blur from the comparison itself) for a side-by-side. Difference is subtle -- slightly softer text edges with Triangle -- and both the person and the model reviewing it found it hard to distinguish at a glance.
  - Went all the way to eliminating supersampling entirely (`SUPERSAMPLE_FACTOR = 1`) as a comparison point too: ~85fps-equivalent (1.48s for the same 120 frames) but broke 5 tests, including one built specifically to prove supersampling beats MSAA alone -- a real, visible AA regression, not just a numeric golden-tolerance miss. Rejected; reverted.
  - Golden PNGs regenerated for the Triangle switch (`cargo run -p renderer-core --example generate_golden` / `generate_golden_svg`) since it intentionally changes render output at every call site that downsamples (PNG renders too, not just GIF -- `finish_frame` is shared). `applies_a_full_canvas_effect_shader_on_an_available_gpu`'s inline tolerance comment/value were updated too (measured delta moved from Lanczos ringing's ~1/255 to Triangle edge-blend's ~5/255; tolerance bumped 4 -> 8) rather than just silently loosened -- the old comment specifically explained *why* via Lanczos ringing, which no longer applies with Triangle.
